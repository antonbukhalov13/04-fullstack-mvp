## 1. Что это за проект

Fullstack MVP учебного финансового сервиса **LumenBridge Finance Ltd** (краткосрочные
займы для физлиц и малого бизнеса в Европе): публичный сайт, личный кабинет
пользователя (вход по OTP) и админ-панель (вход по логину/паролю, роли `admin` и
`operator`).

Источники по контенту и требованиям — файлы в `docs/`:
- `TASK.md` — краткое summary задачи;
- `04-fullstack-task-spec.md` — полное ТЗ и критерии приёмки;
- `04-fullstack-client-content.md` — исходный клиентский текст.

Прочти их до начала работы, не додумывай контент, статусы и бизнес-правила — они
там уже есть. Privacy Policy и Cookie Policy берутся дословно по смыслу из
клиентского текста и переводятся/переносятся — не сочиняются агентом заново.

## 2. Обязательный стек — не менять без согласования

| Часть | Технологии |
|---|---|
| Frontend | Next.js (App Router), React, TypeScript, Tailwind CSS v4 |
| Формы | React Hook Form, Valibot |
| Frontend-архитектура | Feature-Sliced Design |
| Backend | Node.js, NestJS |
| Хранилище | PostgreSQL |

Не предлагай замену (Zod вместо Valibot, Express вместо NestJS, MongoDB вместо
PostgreSQL и т.п.), даже если она кажется удобнее. Если видишь объективную
проблему со стеком — сообщи, но не меняй самостоятельно. Выбор ORM (Prisma —
предпочтительно) — деталь реализации, фиксируется один раз на шаге инициализации
и дальше не меняется.

## 3. Жёсткие ограничения (backend настоящий, но не всё внутри него)

В отличие от этапа 2 (лендинг без backend), здесь backend реальный: все сущности
хранятся в PostgreSQL и переживают перезагрузку страницы и рестарт сервера. Через
mock реализуются только внешние интеграции:

- SMS OTP — код не уходит через реального провайдера, но сам flow (запрос,
  хранение, проверка, срок действия) — реальная backend-логика;
- одобрение заявки — решение оператора вручную в админке, не автоматический
  скоринг;
- платежи — пользователь указывает сумму и reference, администратор вручную
  подтверждает получение денег;
- договор в личном кабинете — статичный mock-документ/заглушка.

В интерфейсе и в README должно быть явно видно, что это имитация, а не реальная
интеграция. Не подключай реальные платёжные шлюзы, реального SMS-провайдера,
внешние скоринговые сервисы.

Загрузка файлов — исключение из списка mock-частей: это реальная интеграция с
S3-совместимым хранилищем (для локальной разработки — MinIO в docker-compose,
доступ по переменным окружения, чтобы в проде можно было подставить настоящий S3).
Через неё реально сохраняются: документы бизнес-заявителя, приложенные к заявке
(Certificate of Incorporation и т.п.), и вложение формы обратной связи. Мокается
не само хранилище, а только то, что "проверка документов" — это ручное действие
оператора в админке, а не автоматическая верификация.

## 6. Server vs Client components / FSD-слои

- **Server (по умолчанию)**: лендинг и его секции, страницы «Как это работает»,
  «Для бизнеса», FAQ, legal-страницы, `layout.tsx`, `generateMetadata`.
- **Client (`"use client"`)**: калькулятор, форма заявки, OTP-формы, весь личный
  кабинет и админ-панель (работают с состоянием и приватными данными), фильтры/
  поиск в админке, любые анимации.
- Компонент становится client только тогда, когда ему реально нужны хуки, события
  браузера или состояние — не помечай `"use client"` "на всякий случай", будь
  готов объяснить каждый конкретный выбор.
- FSD: бизнес-логика (запросы к API, схемы валидации, форматирование) живёт в
  `entities`/`features`/`shared`, а не в компонентах `app`/`pages`.

## 7. Аутентификация и роли

- **Пользователь** — вход по номеру телефона через mock SMS OTP (запрос кода →
  подтверждение → сессия/JWT). Личный кабинет создаётся автоматически при первой
  заявке.
- **Администратор** — вход по логину/паролю. `admin` управляет всеми сущностями и
  учётными записями админки; `operator` работает с заявками, клиентами, займами,
  платежами и уведомлениями, но не управляет ролями и админскими аккаунтами.
- OTP входа в кабинет и OTP подписания займа (`purpose: sign-loan`) — разные
  сущности, не путать их между собой.

## 8. Калькулятор

```
A = P × (r × (1 + r)^n) / ((1 + r)^n − 1)
Total = A × n
```

`A` — размер платежа, `P` — сумма займа, `r = 0.008` (ставка в день), `n` — срок в
днях. Формула реализуется один раз как переиспользуемая функция (backend
`modules/calculator`, дублируется/расшаривается на `frontend/shared/lib` только для
мгновенного клиентского превью). Финальный расчёт при создании займа всегда идёт
через backend. На сайте калькулятор считает только для физлиц (диапазоны 500–50 000
EUR / 7–90 дней), для бизнеса — без автоматического расчёта, только форма заявки
(применение формулы к бизнес-займам — открытый вопрос, см. п.13).

## 9. Полный flow заявки

`Application` (`new → in_progress → approved/rejected`)
→ при `approved` создаётся `Loan` (`pending_signature`)
→ пользователь подписывает через OTP → `Loan.status = active`, фиксируются
  `signedAt`/`signedIp`/`signedUserAgent`
→ backend генерирует `PaymentScheduleItem[]` с шагом в один день: ровно
  `termDays` элементов графика, каждый на сумму `A` (округление последнего платежа
  при необходимости). Для физлиц это подтверждено ментором. Для бизнес-займов
  применение той же аннуитетной формулы, ставки 0.008 и посуточного графика —
  провизорный default до ответа ментора, не финальное решение — см. п.13
→ пользователь создаёт `PaymentRequest`
→ admin/operator подтверждает/отклоняет `PaymentRequest`
→ при подтверждении администратор вручную фиксирует `Payment`
→ если `Payment.amount` больше ближайшего `PaymentScheduleItem.amount` —
  пересчитать оставшийся график
→ когда график полностью погашен — `Loan.status = closed`
→ на каждом переходе статуса создаётся `Notification` для пользователя через
  event bus — см. п.9.1

Не теряй эту связку при реализации по частям: форма заявки, займы и платежи —
разные модули, но один сквозной state flow.

## 9.1. Уведомления через event bus

Уведомления строятся через `@nestjs/event-emitter` (EventEmitterModule):
- **applications, loans, payments, clients** — только emit'ят события (`eventEmitter.emit()`), не импортируют notifications module
- **notifications** — слушает события через `@OnEvent()` и создаёт уведомления в БД

| Модуль | События |
|---|---|
| `applications` | `application.created`, `application.status.changed` |
| `loans` | `loan.created`, `loan.signed`, `loan.schedule.generated`, `loan.closed` |
| `payment-requests` / `payments` | `payment-request.created`, `payment-request.status.changed`, `payment.recorded` |
| `clients` | `payment.overdue` (при проверке просрочек) |

**Важно:** события синхронные (в рамках одного event loop tick). Если listener
в notifications модуле упадёт с ошибкой, это не должно ломать основной бизнес-
процесс (заявка/займ/платёж): оборачивай тело `@OnEvent` в try/catch и логируй
ошибку. Исключение из listener'а не пробрасывается в emitter.

## 10. Личный кабинет

Боковое меню: Заявки, Мои займы, Уведомления. Карточка займа: сумма, ставка, срок,
общая сумма к возврату, график платежей, дата следующего платежа. Действия внутри
карточки: график, mock-договор, создать заявку на оплату, статус заявки на оплату.
Кнопка «Подать новую заявку». Состояния loading/empty/error на каждом разделе.

## 11. Админ-панель

Боковое меню: Заявки, Клиенты, Займы, Платежи, Уведомления. «Заявки» — список +
карточка со сменой статуса и комментарием. «Клиенты» — список с поиском/фильтром +
карточка (контакты, история заявок, активные займы, история платежей). «Займы» —
активные/закрытые, карточка со сменой статуса, отметкой платежа, закрытием.
«Платежи» — заявки на оплату (проверка/подтверждение/отклонение), ручная фиксация
платежей, просрочки. «Уведомления» — системные события.

## 12. Юридические страницы

Полный текст есть только для **Privacy Policy** и **Cookie Policy** — переноси
дословно по смыслу, ничего не сокращай и не добавляй от себя. Terms of Use, Credit
Policy и AML/KYC Policy упомянуты в футере, но текста для них в клиентском контенте
нет: не сочиняй юридический текст самостоятельно — сделай для всех трёх короткую
страницу-заглушку «документ в разработке», один и тот же подход для всех трёх.

## 13. Зафиксированные решения по спорным местам ТЗ

Клиентский текст и ТЗ в нескольких местах не совпадают. Рабочие решения ниже 
менять без причины на середине разработки не нужно:

- бизнес-заявки идут через ту же форму заявки (переключатель «физлицо/бизнес»), а
  не через отдельную форму обратной связи, вопреки формулировке клиентского текста;
- ставка всегда фиксированная `0.008`, «определяется индивидуально» из клиентского
  текста в MVP не реализуется;
- график платежей — посуточный (по одному элементу на каждый день срока), а не по
  неделям — подтверждено ментором для физлиц, до 90 дней;
- загрузка файлов реализована как настоящая интеграция с S3-совместимым
  хранилищем (MinIO локально) — не мок и не ограничение README: документы
  бизнес-заявителя прикрепляются к заявке, вложение формы обратной связи — к
  `ContactMessage`. Проверка содержимого документов остаётся ручным действием
  оператора в админке, автоматической верификации нет.

Открытый вопрос (не додумывать, не реализовывать самостоятельно до ответа):

- применяется ли аннуитетная формула и ставка 0.8%/день к бизнес-займам
  (диапазон 30 000–500 000 EUR / 1–12 месяцев), или для бизнеса расчёт вообще не
  показывается, раз заявки идут через специалиста. Текущий provisional-default —
  использовать ту же формулу/ставку при создании займа после одобрения (см. п.9),
  но **не** показывать автоматический калькулятор для бизнеса на сайте — только
  форма заявки. При получении ответа от ментора обновить этот пункт и п.9.

## 16. Ведение AI_USAGE.md

После выполнения **каждого** запроса/промпта добавляй запись в `AI_USAGE.md` в
корне проекта (если файла нет — создай). Формат — заголовок `## Request N`, дальше
поля строго в этом порядке:

```
## Request N

Goal: краткая цель запроса, одно предложение

Prompt: номер шага из PROMPT_PLAN.md — краткое название

полный текст промпта, который был отправлен агенту

Result: кратко что реально сгенерировано/изменено — конкретные файлы, модули,
компоненты, ключевые технические решения

Used as-is / edited manually / rejected: выбрать один вариант

What I learned: краткий вывод — что можно было сформулировать точнее

Model used: [актуальная модель]

Provider used: [актуальный провайдер]

Instrument used: OpenCode
```

Веди файл самостоятельно по умолчанию после каждой завершённой задачи, не спрашивая
отдельного разрешения. Поле `Used as-is / edited manually / rejected` агент не
может определить сам — если пользователь не указал явно, ставь `used as-is`.

## 17. Коммиты

Коммиты должны отражать рабочие этапы. Один коммит — один осмысленный шаг (обычно
соответствует одному Request из PROMPT_PLAN.md), а не «WIP» или «fix» без
контекста. Сообщение — в повелительном наклонении, на английском, коротко, без
точки в конце.
 
Примеры хороших сообщений:

```
init project structure
add landing hero and services sections
add lead form validation
add crm lead status filter
add backend leads endpoints
connect frontend lead form to api
```

## 18. Чего агенту делать не нужно

- Не нужно подключать реальные платёжные интеграции, реального SMS-провайдера, внешние
  скоринговые сервисы.
- Не нужно хранить реальные секреты/персональные данные, не коммитить `.env` с боевыми
  значениями.
- Не нужно путать OTP входа в кабинет и OTP подписания займа.
- Не нужно связывать заявку и займ «напрямую в UI» в обход backend-статусов.
- Не нужно сочинять юридический текст для Terms/Credit Policy/AML-KYC — см. п.12.
- Не нужно сочинять текст, которого нет в файле с клиентским контентом
- Не нужно менять обязательный стек и не добавлять сторонние UI-киты без необходимости.
- Не нужно сваливать backend-логику в контроллеры без сервисного слоя.
- Не нужно заполнять README.md, пока не попросят.
- Не нужно показывать автоматический калькулятор для бизнес-займов на сайте и не
  считать этот вопрос закрытым.
- Не нужно путать mock-статус остальных внешних интеграций (SMS, скоринг, платёжный
  провайдер, договор) с загрузкой файлов — она реальная, см. п.3.

  ## 19. Чего агенту делать нужно

- Нужно в конце каждого промпта сверяться с клиентским контентом (и ТЗ) —
  реализованное не должно расходиться с текстом источника, особенно тексты
  страниц и юридических разделов.
- Нужно вести `AI_USAGE.md` после каждого выполненного запроса — формат см. в п.16.
- Нужно писать название для коммита после каждого выполненного запроса — формат см. в п.17.

После каждого выполненного запроса нужно убедиться, что проект в рабочем
состоянии, прежде чем переходить к следующему шагу или коммитить:
 
- backend и frontend запускаются без ошибок (`npm run build`/`npm run start:dev`,
  `npm run dev`/`npm run build` — по месту);
- новый или изменённый код не ломает то, что уже было сделано в предыдущих
  запросах (быстрая ручная проверка соответствующего сценария, а не только
  компиляция);
- если запрос добавлял backend-эндпоинт — проверить его вызовом (curl/Postman/
  Swagger), а не полагаться на то, что код «выглядит правильно».

Если после запроса что-то не работает — это фиксируется и чинится в рамках того
же шага, а не переносится молча на следующий запрос.
